TAYLER ERBE / PIPELINE DESIGN · RESEARCH PROPOSALS AND AWARDS

Read every proposal and award, and show the evidence.

Sponsored-research offices hold thousands of proposal narratives and award documents that no report can see. This pipeline reads them with local models and turns them into searchable, filterable fields, each tied to the passage it came from.

Short answer: take every fact that already lives in a database column from the database. Ask the model only for what lives in the text, make it point to the passage, and let code copy the quote.

01 / THE PIPELINE

An assembly line,
one model at a time.

Each stage runs across the whole corpus, then unloads its model before the next stage starts. Small task-specific models often beat one large general model, and the target hardware holds one model comfortably.

  1. Ingest
  2. Parse
  3. Classify
  4. OCR unread pages
  5. Extract fields
  6. Consolidate
  7. Export and review
Deterministic codeLocal model

  1. Ingest by fingerprint

    Each file is registered by the SHA-256 of its bytes. A boilerplate plan attached to five proposals is read once and keeps all five links, which come from source-system IDs, never from file names.

  2. Parse with read states

    PDFs keep page and position; Word files keep paragraph and table-row identity. A scanned page is marked unread until OCR succeeds. Unsupported formats stay visible with a reason.

  3. Classify by metadata first

    Proposal or award comes from the document's role in the source system. Type (narrative, biosketch, notice of award, modification) comes from attachment codes, then file names, then opening text. Otherwise "other".

  4. Read what has no text

    A vision model transcribes only the unread pages. Its text is stored as unverified OCR, separate from native text, so later reviews know where each word came from.

  5. Extract with evidence IDs

    Every readable passage goes to the field model in bounded chunks, labelled E1, E2, and so on. The model returns IDs and choices. Code copies the exact text and rejects anything it cannot resolve.

  6. Consolidate, then review

    Code merges the chunks by fixed rules, keeps conflicting answers, and exports long, wide and case-level tables with an offline review page and full-text search.

!

"Not found" is not "absent".

A field is reported as not found in the full text only when every chunk was read and answered. If a page is still unread, the result says so. A truncated or malformed model answer is a failure, never an absence.

Ask the model only
what the text knows.

Sponsor, amounts, dates, investigators, units and funding outcome already sit in database columns. Asking a model to re-read them only adds errors. The model's job is the narrative: what the work is, what it needs, and what the award requires.

Built so a wrong
answer is visible.

A pipeline that reads thousands of documents will be wrong sometimes. The design goal is that every error can be seen, traced to a passage, and corrected without losing the original.

01 / EVIDENCE

IDs, not quotes

The model never writes a quote. It names excerpt IDs; code copies the text and rejects unknown IDs, off-list values and "found" with no evidence.

02 / ABSENCE

Earned, not assumed

"Not found" is only reported for text that was read. Unread pages, failed chunks and truncated answers each get their own state.

03 / TIME

No look-ahead

The case table keeps award documents in separate award columns, so facts known only after a decision can never explain whether a proposal was funded.

04 / LINEAGE

Nothing overwritten

Each result carries the model digest, prompt hash and schema version. A new model makes a new version; a reviewer's correction never replaces the original proposal.

foundA value with at least one resolved passage. Still a proposal until a person accepts it.
ambiguousDifferent chunks chose different single values. Both are kept for review.
not found in full textEvery readable chunk answered and nothing was found. Not a legal statement of absence.
not found in read textNothing found, but some pages are still unread.
no readable textThe document has no text yet, such as an image-only scan awaiting OCR.
incompleteA chunk failed, was truncated or was rejected, so the field cannot be called.

Local only. Inference runs on approved on-premises hardware through a local model server. The pipeline refuses to substitute a model that is not installed and refuses to start while another workload holds the GPU.

Next: real documents,
real labels.

A paired sample of funded proposals with their awards, and matched unfunded proposals, has already been pulled read-only from the source system. The next steps turn the prototype into evidence.

01 / AGREE

Lock the fields

Review the 18 provisional fields with the sponsored-programs owner: definitions, single or multiple values, and what counts as evidence.

02 / RUN

The paired sample

Run locally on the paired proposals and awards in small batches, review the outputs, and fix what real documents break.

03 / LABEL

A locked holdout

Label 100–300 representative documents, double-label a fifth of them, adjudicate, and score against a holdout no one tunes on.

04 / ROUTE

Provision the parsers

Stand up the selected table and page parsers on-prem behind the same interface, then join fields to database facts for analysis.

Why synthetic first. Fabricated documents with known answers let every stage, failure state and model adapter be tested before a single real document is touched, and they can be shared openly.
